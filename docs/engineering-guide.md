## 1. 先说结论：你需要学什么，不需要学什么

**你不需要学会写代码。你需要学会"驾驭"：说清楚要什么，判断做得对不对，并且搭好让 AI 不跑偏的护栏。**

这其实就是第 6 节要讲的 "Harness" 的意思。你已经在做其中最难的部分了：`spec.md` 里写了目标、非目标、验收标准，这是很多程序员都做不好的事。

| 优先级 | 内容 | 为什么 |
|---|---|---|
| ★★★ 必学 | **写清楚需求和验收标准** | 你已经在做。AI 做得好不好，七成取决于这一步 |
| ★★★ 必学 | **写好 Bug 报告和体验反馈**（第 7 节） | 这是你最大的痛点，也是最容易提升的技能 |
| ★★★ 必学 | **在预览链接上验收**（第 4.2、7.6 节） | "完成"必须由你确认，而不是 AI 自己宣布 |
| ★★★ 必学 | **评测 AI 对话质量**（第 7.7 节） | Chat the Day 的核心价值，你是最合适的评委 |
| ★★ 了解 | Git / GitHub 的五个概念：仓库、提交、分支、PR、合并 | 看懂工作进度，知道什么时候该你出手 |
| ★★ 了解 | 每个技术组件大概是干什么的 | 能听懂 AI 在说什么，能判断它的建议是否合理 |
| ★★ 了解 | 密钥与隐私的基本常识（第 4.3 节） | 避免最常见、后果最严重的事故 |
| ★★ 了解 | MCP、上下文窗口等 AI 概念 | 知道工具能做什么、为什么 AI 会"忘事" |
| ★ 暂时不用 | 编程语言（TypeScript/React）、SQL、CSS | AI 负责；你需要的话以后再学 |
| ★ 暂时不用 | 服务器、Docker、运维 | Vercel 和 Supabase 已经替你做了 |

## 2. Soul Matter 是怎么运转的

### 2.1 一张图

```
         你 / 朋友
     （手机或电脑浏览器）
              │
              │ HTTPS（加密传输）
              ▼
  ┌───────────────────────────────┐        ┌──────────────────────────┐
  │  Vercel（托管平台）             │        │  Supabase（托管数据库）    │
  │  ┌─────────────────────────┐  │        │  ┌────────────────────┐  │
  │  │ Next.js 应用             │  │ ─────▶ │  │ Auth 登录与账号     │  │
  │  │  · 页面（首页、详情…）    │  │        │  │ PostgreSQL 数据库   │  │
  │  │  · 接口 /api/...         │  │ ◀───── │  │ RLS 行级权限        │  │
  │  └─────────────────────────┘  │        │  └────────────────────┘  │
  └───────────────────────────────┘        └──────────────────────────┘
              │
              │（M2 起）
              ▼
  ┌───────────────────────────────┐
  │  DeepSeek（大模型 API）        │
  └───────────────────────────────┘

  GitHub（存放代码） ──推送代码后自动通知──▶ Vercel 重新构建并上线
```

### 2.2 一个比喻：开一家餐厅

| 餐厅 | Soul Matter | 说明 |
|---|---|---|
| 前厅（菜单、座位、服务员） | **前端**：你在浏览器里看到的页面 | 用 React 组件拼成，用 Tailwind 装修 |
| 后厨 | **后端**：`/api/...` 接口、服务端逻辑 | 接收请求、检查身份、读写数据 |
| 仓库 | **数据库**：Supabase PostgreSQL | 心事、标签、Panel 都存在这里 |
| 门卫 + 每个储物柜的锁 | **Auth + RLS** | Auth 确认"你是谁"；RLS 保证"你只能开自己的柜子" |
| 外请的大厨 | **DeepSeek** | 按次付费，按我们的"菜谱"（prompt）做菜 |
| 商场物业 | **Vercel** | 水电、门面、保安都不用你管；你只管把菜谱（代码）交过去 |
| 菜谱本 | **GitHub 仓库** | 所有代码的唯一正本，每次修改都有记录 |

### 2.3 跟着一次点击走一遍

当你在首页点开一条心事：

1. 浏览器向 `soulmatter.vercel.app/zh/entries/xxx` 发出请求
2. Vercel 上的 **proxy**（中间件，门口的保安）先检查：你登录了吗？要用哪种语言？
3. Next.js 找到对应的**页面文件** `src/app/[locale]/entries/[id]/page.tsx`
4. 页面代码让 Supabase 查"这条心事"；Supabase 的 **RLS** 检查这条心事是不是你的
5. 数据返回，页面拼成 HTML 发回浏览器，你看到详情

M1 里"点卡片 404"的 bug，就出在第 2 步：保安没有把不带 `/zh` 的地址正确地领到对应的房间。

## 3. 每个组件：是什么、为什么选它、代价是什么

技术选型永远是**取舍**。没有"最好的"工具，只有"在你的约束下最合适的"。你的约束是：不写代码、预算低、自己和朋友用、AI 开发。

| 组件 | 一句话 | 为什么选它 | 代价 / 要注意 |
|---|---|---|---|
| **Next.js 16** | 网站框架，页面和接口写在同一个项目里 | 一个项目搞定前后端；Vercel 原生支持；AI 最熟悉的生态之一 | **版本很新**，AI 训练数据里多是旧写法。`AGENTS.md` 就是为此提醒 AI "先读文档"。M1 的中间件问题就是这个坑 |
| **React** | 把页面拆成一个个"组件"（卡片、按钮、导航栏）来拼 | Next.js 的基础 | — |
| **TypeScript** | 带"类型"的 JavaScript | 像给表格每列规定格式（日期列不能填文字），写错时提前报错。对 AI 写代码来说是**免费的第一道质检** | 无 |
| **Tailwind CSS** | 写样式的一种方式 | AI 写起来快且风格一致 | Markdown 排版需要额外插件（M1 的 Panel 问题） |
| **Supabase** | 托管的数据库 + 登录 + 权限 + 向量检索 | 免费额度够用；一站式；不用自己管服务器 | 免费版目前的政策是**一周无访问会自动暂停**（以官方为准）；**项目管理员（你）能看到所有用户的数据** |
| **Vercel** | 网站托管与自动部署 | 推送代码就自动上线；**每个分支自动生成预览网址**（对你验收非常重要） | 免费版仅限非商业用途；单次请求的执行时间有上限，做流式对话时需要留意 |
| **DeepSeek** | 大模型 API | 中文好、便宜；接口与 OpenAI 兼容，以后换模型成本低 | 对话内容会发送给第三方；AI 的行为全靠 prompt 约束 |
| **next-intl** | 多语言 | Next.js 生态中最常用的方案 | 每个页面的文案要维护两份 |
| **react-markdown** | 把 Markdown 文字显示成排版好的内容 | 简单可靠 | — |
| **GitHub** | 代码仓库 + 协作平台（Issue、PR、自动检查） | 行业标准；Vercel 直接对接 | — |
| **npm / package.json** | 项目的"配料表" | `package.json` 写需要哪些第三方包；`package-lock.json` 是精确到批次的采购单，保证每台电脑装的完全一样 | 不要手改 lock 文件 |
| **ESLint** | 代码检查员 | 抓常见错误和不规范写法 | — |
| **GitHub Actions** | 自动检查（CI） | 每次提交自动跑 lint、类型检查、构建和 E2E 测试，PR 上显示 ✅ 或 ❌ | 每次运行要几分钟 |
| **Playwright** | 自动化浏览器测试（E2E） | 像真人一样打开网站、注册、写心事、点按钮、检查结果 | 测试要随功能一起维护 |
| **本地 Supabase（Docker）** | 测试专用的临时数据库 | CI 每次运行时临时启动，用 `schema.sql` 建表，测完即丢，**不碰线上数据** | `schema.sql` 必须和线上保持一致 |
| *计划中* **zod** | 数据格式校验 | 检查环境变量、接口参数、AI 返回的 JSON 是否合规 | — |

### 3.1 仓库里的文件夹是干什么的

```
Soul_Matter/
├── docs/                  ← 你最常看的地方：规格、任务、评审、本指南
│   └── acceptance/        ←   每个里程碑的人工验收清单
├── src/
│   ├── app/               ← 页面和接口。文件夹结构 = 网址结构
│   │   ├── [locale]/      ←   带语言的页面（中文不带前缀，英文为 /en/...）
│   │   │   └── (app)/     ←     登录后才能看的页面（括号表示不影响网址）
│   │   ├── api/           ←   后端接口（/api/entries、/api/panel）
│   │   └── auth/          ←   登录、注册、退出、邮箱确认
│   ├── components/        ← 可复用的组件（顶栏、登录卡片、语言切换）
│   ├── i18n/              ← 多语言配置
│   ├── lib/               ← 工具代码（连接 Supabase 等）
│   ├── types/             ← 数据类型定义
│   └── proxy.ts           ← 门口的"保安"：语言路由 + 登录保护
├── messages/              ← 多语言文案（zh.json / en.json）——纯文字，你可以直接改
├── supabase/              ← 数据库结构（schema.sql）和变更脚本（migrations/）
├── e2e/                   ← 自动化浏览器测试 + 测试数据库配置
├── .github/               ← CI 配置（workflows/）和 Issue 反馈表单
├── AGENTS.md / CLAUDE.md  ← 给 AI 看的项目规则（含"完成的定义"）
└── package.json           ← 依赖清单和常用命令
```

## 4. 代码从写出来到上线的旅程

### 4.1 Git 的五个核心概念

把代码想象成一本**多人合写的书**：

| 概念 | 书的比喻 | 在 Soul Matter 里 |
|---|---|---|
| **仓库 Repository** | 这本书的全部内容和修改历史 | `github.com/JoekyRio/Soul_Matter` |
| **提交 Commit** | 一个"存档点"，附一句说明 | 例如 `feat: complete M1 homepage refactor` |
| **分支 Branch** | 平行的草稿本，不影响正式版 | `main` 是正式版；`feature/phase2-m1`、`claude/...` 是草稿 |
| **拉取请求 Pull Request（PR）** | "请审稿，我想把草稿并入正式版" | 一个网页：能看到改了什么、自动检查结果、讨论、预览链接 |
| **合并 Merge** | 审稿通过，草稿成为正式版 | 合并到 `main` 后，Vercel 自动更新正式站 |

提交说明的前缀约定：`feat:` 新功能，`fix:` 修 bug，`docs:` 文档，`refactor:` 重构（不改变功能的代码整理），`test:` 测试。

### 4.2 三个环境

| 环境 | 谁在用 | 地址 | 用途 |
|---|---|---|---|
| **本地 Local** | AI（在它的电脑/容器里） | `localhost:3000` | 开发和初步自测 |
| **CI 测试** | 机器（GitHub Actions） | 无，每次提交临时搭建，测完即丢 | 自动跑全部检查和 E2E 测试，使用临时的本地数据库 |
| **预览 Preview** | **你**（验收） | 每个分支/PR 自动生成一个独立网址，Vercel 会把链接贴在 PR 页面上 | 合并前验收，不影响正式站 |
| **正式 Production** | 你和朋友（日常使用） | `soulmatter.vercel.app` | 真实使用 |

⚠️ **注意**：目前预览环境和正式环境连的是**同一个 Supabase 数据库**。在预览链接上新建、删除的心事都是真实数据。建议注册一个**测试账号**专门用来验收。以后可以为预览环境单独建一个测试数据库。

**黄金规则：不在正式站上调试。** 问题在预览环境复现、修复、验收，再合并上线。

### 4.3 环境变量与密钥

**环境变量**是"不写在代码里的配置"，例如数据库地址、API 密钥。它们存在 Vercel 的项目设置里，代码运行时去读。

| 规则 | 原因 |
|---|---|
| 名字以 `NEXT_PUBLIC_` 开头的变量**会被发到浏览器里**，任何人都能看到 | 所以只放可以公开的东西 |
| Supabase 的 `anon key` 可以公开 | 它本身没有特权，安全靠 RLS 保证 |
| Supabase 的 `service_role key` **绝对不能**放进前端或 `NEXT_PUBLIC_` | 它能绕过所有权限，等于万能钥匙 |
| `DEEPSEEK_API_KEY` 只在服务端使用，**不加** `NEXT_PUBLIC_` | 泄露后别人可以用你的额度 |
| **永远不要**把密钥贴进聊天窗口、截图、提交到 GitHub | 一旦泄露就要去后台作废、重新生成 |

### 4.4 数据库变更（Migration）

改代码可以随时撤销，但**改数据库结构影响的是真实数据**。所以：

1. 每次结构变更写成一个编号的迁移脚本：`supabase/migrations/001_...sql`、`002_...sql`，按顺序执行
2. 脚本由你在 Supabase 控制台 → SQL Editor 里执行（AI 会附上步骤）
3. 涉及删除或修改已有字段时，先在 Supabase 里备份
4. `schema.sql` 是"从零建库"的完整版本，迁移脚本是"在已有数据库上增量修改"的版本，两者要保持一致

## 5. 程序员如何协作，以及你和 AI 如何协作

### 5.1 标准流程

一个功能在专业团队里通常这样走：

```
 Issue ──▶ 分支 ──▶ 开发 ──▶ PR ──▶ 自动检查(CI) ──▶ 代码审查 ──▶ 预览验收 ──▶ 合并 ──▶ 自动部署 ──▶ 线上验证
（要做什么） （草稿）         （申请合并）  （机器把关）     （人/AI 把关）   （产品把关）
```

每一道关都在拦截不同类型的问题：
- **CI** 拦截"代码写错了"（语法、类型、构建失败、自动化测试不通过）
- **代码审查** 拦截"代码写得不好或不安全"（Phase 1 的独立审查就拦下了一个高危权限漏洞）
- **预览验收** 拦截"做出来的东西不是我要的"——**这一关只有你能把**

M1 的问题，就是因为 CI 和审查两道关都还没建立，而验收这一关被跳过了。

### 5.2 角色对照

| 专业团队里的角色 | 在 Soul Matter 里由谁担任 |
|---|---|
| 产品经理（定义做什么、为什么） | **你** |
| 设计师（长什么样、怎么交互） | **你** 提方向和感受 + AI 实现 |
| 开发工程师 | AI（Claude Code / TRAE） |
| 自动化测试 | CI + Playwright（M1.5 建立） |
| 代码审查者 | 另一个 AI 会话做独立审查（不让写代码的同一个会话审查自己） |
| 验收测试 / 首席体验官 | **你** |
| 运维 | Vercel + Supabase |

### 5.3 文档体系：文档是 AI 的长期记忆

AI 每开一个新对话都会"失忆"，它对项目的了解全部来自仓库里的文件。所以**文档写得越清楚，AI 越不容易跑偏**。

| 文件 | 回答什么问题 | 谁维护 |
|---|---|---|
| `docs/spec.md` | 做什么、为什么、不做什么 | 你主导，AI 协助 |
| `docs/tasks.md` | 怎么做、按什么顺序、怎样算完成 | AI 起草，你确认 |
| `docs/product-review.md` | 产品方向的评审与决策 | 本次评审 |
| `docs/review.md` | 代码审查记录 | 审查方 |
| `docs/acceptance/*.md` | 每个里程碑的人工验收清单（已有 M1） | AI 起草，你执行 |
| `prompts/*.md`（计划中） | AI 的"人设"和规则、测试剧本、评分表 | **你可以直接编辑** |
| `AGENTS.md` | 给所有 AI 工具的项目规则 | 共同维护 |

### 5.4 一个任务的完整生命周期

| 步骤 | 你 | AI | 自动化 |
|---|---|---|---|
| 1. 提出 | 描述想要什么、为什么；或指定 tasks.md 里的任务 | 复述理解，提出疑问 | — |
| 2. 计划 | 确认方案（大任务） | 列出要改哪些地方、怎么验收 | — |
| 3. 开发 | 不用管 | 在分支上写代码，本地跑检查 | — |
| 4. 提交 | — | 推送分支，开 PR | CI 自动运行；Vercel 生成预览链接 |
| 5. 审查 | — | 另一个会话独立审查（重要改动） | CI 结果显示在 PR 上 |
| 6. 验收 | **打开预览链接，按清单在手机和电脑上走一遍**，问题提成 Issue | 修复问题，重复 4–6 | — |
| 7. 合并 | 点"Merge"（或让 AI 合并） | — | Vercel 自动部署正式站 |
| 8. 收尾 | 正式站上快速检查 | 更新 tasks.md 状态和相关文档 | — |

### 5.5 "完成"的定义（Definition of Done）

一个任务只有同时满足以下条件，才能标记为 `completed`：

- [ ] CI 全绿（lint、类型检查、构建、自动化测试）
- [ ] 任务里列出的每条测试要求（TR-xx）都有证据
- [ ] 你在预览链接上验收通过
- [ ] 相关文档已更新（tasks.md 状态、README、迁移步骤等）
- [ ] 数据库变更已在 Supabase 执行（如有）

### 5.6 同时使用 TRAE 和 Claude Code 的规则

- **一个分支同一时间只让一个 AI 改**，否则会互相覆盖、产生冲突
- 共享的项目规则写进 `AGENTS.md`（会提交到仓库，所有工具都能读到）。你的 `.gitignore` 排除了 `.trae/` 目录，写在那里的规则其他工具看不到
- 换工具前，先让当前的 AI 把工作提交并推送到 GitHub

## 6. 概念扫盲：Vibe Coding、Harness、MCP 及其他

| 概念 | 一句话 | 和你的关系 | 需要学吗 |
|---|---|---|---|
| Vibe Coding | 只描述想要什么，不看代码，AI 写什么就用什么 | 你现在的起点，也是 M1 出问题的原因 | 理解它的边界 |
| Spec-driven 开发 | 先写规格和验收标准，再让 AI 实现 | 你已经在做，继续 | ★★★ |
| AI Coding Agent | 能自己读文件、改代码、跑命令的 AI | TRAE SOLO、Claude Code 都是 | 会用即可 |
| **Harness** | 让 AI 稳定干活的"工作环境" | **你最值得投入学习的概念** | ★★★ |
| MCP | 让 AI 工具连接外部系统的通用"插头" | 能让 AI 直接看数据库结构、操作浏览器 | ★★ 了解 |
| Rules / AGENTS.md / Skills | 写给 AI 的项目说明书 | 高杠杆，你可以参与写 | ★★ |
| 上下文窗口 / Token | AI 一次能"记住"的内容量 / 计费单位 | 解释 AI 为什么会忘事、为什么要开新对话 | ★★ |
| Prompt / System Prompt | 给 AI 的指令 / 给 AI 设定的"人设和规则" | Chat the Day 的灵魂 | ★★★ |
| RAG | 让 AI 回答前先去资料库里查 | 原 Phase 3 的知识库 | ★ 了解 |
| Eval（评测） | 用固定的测试题给 AI 打分 | 测试剧本就是 eval | ★★★ |
| CI/CD | 自动检查 / 自动部署 | PR 上的 ✅❌；Vercel 自动上线 | ★★ 看懂 |

### 6.1 Vibe Coding（氛围编程）

2025 年初由 AI 研究者 Andrej Karpathy 提出：用自然语言告诉 AI 你想要什么，**不读代码**，跑起来就接受，出错就把错误信息丢回给 AI。

- **它的好处是真实的**：你一个人、不懂代码，几天内就做出了能登录、能存数据、部署在线上的应用
- **它的边界也是真实的**：项目越大，"看起来能用"和"真的能用"之间的差距越大。M1 就是例子：首页看起来完成了，但点进卡片就 404，Task 却标记为 completed

**解法不是去学写代码，而是把"信任"换成"验证"**：规格写清楚 → 自动检查把关 → 独立审查 → 你来验收。这就是从 Vibe Coding 升级到下面说的 Harness。

### 6.2 Harness（驾驭）——你最值得学习的概念

Harness 的原意是套在马身上的挽具，让马的力气能用来拉车。在 AI 领域有两层意思：

**第一层：Agent Harness（智能体外壳）**——把一个大模型包装成能干活的智能体的那套软件：让它能读写文件、运行命令、管理记忆、请求权限。Claude Code、TRAE SOLO、Cursor 都是 harness。对你来说，选哪个工具没有想象中重要。

**第二层：Harness Engineering（驾驭工程）**——近一两年在 AI 开发圈流行起来的说法：当 AI 能写大部分代码时，人的工作重心转向**为 AI 搭建工作环境**，让它在护栏里稳定产出：

| 护栏 | 在 Soul Matter 里 | 谁来做 |
|---|---|---|
| 清晰的目标和边界 | `spec.md`（含非目标、验收标准） | 你 ✅ 已有 |
| 拆小的任务 + 明确的"完成"标准 | `tasks.md` | AI 起草，你确认 ✅ 已有 |
| 项目规则 | `AGENTS.md` | 共同 |
| 自动检查 | CI：lint、类型检查、构建、冒烟测试 | AI 搭建（M1.5） |
| 独立审查 | 另一个 AI 会话审查代码 | 流程约定 |
| 人工验收 | 验收清单 + 预览链接 | 你 |
| AI 行为的评测 | 测试剧本 + 评分表 | 你 + AI（M2） |

**这就是你在这个项目里的"工程化"工作。** 你不需要会写代码，但需要会设计和维护这些护栏。

### 6.3 MCP（Model Context Protocol，模型上下文协议）

2024 年底由 Anthropic 提出、现在被主流 AI 工具普遍支持的开放标准。可以把它理解为 **AI 工具的"USB-C 接口"**：任何外部系统只要做一个 MCP 插头，任何支持 MCP 的 AI 工具都能连上去用。

和 Soul Matter 可能相关的 MCP：

| MCP | 能让 AI 做什么 | 建议 |
|---|---|---|
| GitHub MCP | 读写 Issue、PR、查看 CI 结果 | 我（Claude Code）在这个环境里已经在用 |
| Supabase MCP | 直接查看数据库结构、执行查询 | 有用；**只给只读权限，且只连测试项目** |
| Playwright / 浏览器 MCP | 让 AI 打开浏览器点击、截图、检查页面 | 有用，适合 UI 自测 |
| Next.js DevTools MCP | 让 AI 读取运行中的 Next.js 的报错和路由信息 | Next.js 16 官方支持，可选 |

**需要学到什么程度**：知道 MCP 是什么、知道在 TRAE 里怎么打开某个 MCP 即可。安全原则：**连接越多、权限越大，出事的影响越大**。能只读就只读，能连测试环境就不连正式环境。

### 6.4 Rules 文件 / AGENTS.md / Skills

- **AGENTS.md**：放在仓库根目录、写给所有 AI 工具的"项目说明书"。你的项目里已经有了（目前只有 Next.js 版本提醒）。`CLAUDE.md` 里的 `@AGENTS.md` 表示"Claude 请读 AGENTS.md"
- **Rules**：各工具自己的规则文件（例如 TRAE 的项目规则）
- **Skills**：可以按需加载的"操作手册"，例如"如何发布一个新版本"

建议以后往 `AGENTS.md` 里补充：完成的定义、提交规范、"先读 docs/spec.md 和 docs/tasks.md"、"数据库变更必须写迁移脚本"等。

### 6.5 上下文窗口与 Token

- **Token**：AI 处理文字的单位。按 DeepSeek 官方的估算，一个汉字约 0.6 个 token。DeepSeek 按 token 收费
- **上下文窗口**：AI 一次能"看到"的内容上限。对话越长，越早的内容越容易被压缩或遗忘

**实际影响**：
- 一个对话做一件事；对话变得很长、AI 开始犯糊涂时，开新对话
- 重要的结论让 AI **写进文档**，而不是只留在聊天记录里
- Chat the Day 也一样：一段对话很长时，要控制发给 DeepSeek 的历史长度（成本和质量都受影响）

### 6.6 Prompt 与 System Prompt

- **Prompt**：你给 AI 的指令
- **System Prompt**：在对话开始前给 AI 设定的身份、规则和边界，用户看不到

Chat the Day 的 AI "像不像一个好的陪伴者"，几乎完全由 system prompt 决定。M2 会把它放在 `prompts/chat-guide.md` 这个**纯文字文件**里——**你可以直接打开修改**，这是你参与产品核心最直接的方式。

### 6.7 RAG（检索增强生成）

让 AI 回答前，先去一个资料库（例如 CBT 教材的段落）里检索相关内容，把找到的内容和问题一起交给 AI。用到的技术包括 **Embedding**（把文字变成可比较的数字向量）和**向量数据库**（Supabase 的 pgvector）。

**好处**：回答有据可依、可以引用出处。**代价**：资料收集、切分、检索调优的工作量大。新计划建议先用 prompt + 测试剧本验证，确实不够再上 RAG（评审文档 D6）。

### 6.8 Eval（评测）

用一套**固定的测试题**给 AI 打分，每次修改 prompt 或换模型后重新跑一遍，看分数是升还是降。没有 eval，改 prompt 就是凭感觉——今天修好了 A 场景，可能不知不觉弄坏了 B 场景。

你的"测试剧本 + 评分表"就是 Soul Matter 的 eval。详见 7.7。

### 6.9 其他常听到的词

- **Hallucination（幻觉）**：AI 一本正经地编造不存在的事实。在心理领域尤其危险，所以 prompt 里要约束"不确定就说不确定"
- **Streaming（流式输出）**：AI 回复一个字一个字地出现，而不是等全部生成完再显示
- **Lint / Typecheck / Build / Test**：四种自动检查，分别查"写法规范""类型正确""能否打包""功能是否符合预期"
- **Refactor（重构）**：不改变功能的代码整理
- **Regression（回归）**：改 A 的时候把原本好的 B 弄坏了。自动化测试的主要作用就是防回归

## 7. 你如何高效参与测试与优化（重点）

### 7.1 你的角色

你是 **产品负责人 + 首席体验官 + 最终验收人**。

你不需要读代码，你需要判断两件事：
1. **行为对不对**——点了这里，应该发生什么？实际发生了什么？
2. **感觉好不好**——用的时候顺不顺、安不安心、想不想再用？

第 2 件事，任何工程师和 AI 都无法替代你。

### 7.2 四种反馈，四种写法

| 类型 | 特征 | 用什么模板 |
|---|---|---|
| 🐞 **Bug** | 坏了：报错、404、点了没反应、数据不对 | 7.3 Bug 报告 |
| 😣 **体验问题** | 没坏，但不舒服：找不到、看不懂、太慢、有压力 | 7.4 体验反馈 |
| 💡 **新想法** | "如果能……就好了" | 写清楚"在什么场景下、想解决什么问题" |
| 🤖 **AI 回复质量** | AI 说得不好：说教、贴标签、跑题、太长 | 7.7 AI 质量反馈 |

本次一起提交了对应的四个 **GitHub Issue 表单**（`.github/ISSUE_TEMPLATE/`，合并到 `main` 后生效）：打开 GitHub 仓库 → Issues → New issue → 选择模板，按格子填就行，截图和录屏可以直接拖进去。不想用 GitHub 时，直接在对话里按同样的结构发给我也可以。

### 7.3 Bug 报告：六个要素

```
【在哪】   哪个页面（直接复制浏览器地址栏的网址最好）
【步骤】   1. …  2. …  3. …（从一个明确的起点开始，比如"登录后在首页"）
【期望】   应该发生什么
【实际】   实际发生了什么（原样抄下错误文字）
【证据】   截图或录屏
【环境】   设备 + 浏览器；正式站还是预览链接；大概几点（方便查日志）
```

**示例（M1 的真实 bug）**：

> **在哪**：soulmatter.vercel.app/zh（已登录）
> **步骤**：1. 登录后在首页 2. 点击左侧任意一张心事卡片
> **期望**：进入这条心事的详情页
> **实际**：显示 404 页面，网址变成了 `/entries/xxxx`（没有 `/zh`）
> **证据**：截图
> **环境**：iPhone / Safari，正式站，10 月 6 日 21:00 左右

有了这六个要素，AI 往往一次就能定位问题。最关键的是**步骤**和**期望 vs 实际**。

### 7.4 说清楚"不舒服"：五步法

体验问题最难描述，因为它通常是一种模糊的感受。用这五步把它变具体：

1. **我想做什么**（目标）："我想在睡前快速记一下今天开会时的委屈"
2. **我做了什么**（动作）："打开网站 → 找写心事的按钮"
3. **在哪一步卡住了**（摩擦点）："首页没找到写心事的按钮，找了十几秒"
4. **我的感受**（用下面的词汇表 + 1–5 分）："烦躁，3 分；差点就不记了"
5. **我希望怎样**（期望，可以参考别的 App）："打开就能直接写，像备忘录那样，或者首页有个明显的大按钮"

**描述感受的词汇表**（挑一个最接近的）：

| 感受 | 通常意味着 |
|---|---|
| 找不到 | 入口位置或标识有问题 |
| 看不懂 | 文案或图标不清楚 |
| 点了没反应 / 不确定点没点上 | 缺少加载状态或操作反馈 |
| 等太久 | 性能问题，或者缺少"正在处理"的提示 |
| 太挤 / 太空 / 太乱 | 布局、间距、信息层级 |
| 被打断 | 弹窗或跳转时机不对 |
| 有压力 / 被评判 | 文案语气、AI 语气、必填项太多 |
| 不放心 | 隐私、数据会不会丢、操作能不能撤销 |
| 不想再用 | 最重要的信号，务必说出来，哪怕说不清原因 |

**界面部件的名称**（说清"哪里"）：

```
┌──────────────────────────────────────────────────────────┐
│ 导航栏 / 顶栏  [LOGO]                  [语言切换] [头像] [退出] │
├──────────────────────┬───────────────────────────────────┤
│ [ 搜索框 ………… ]       │  入口区（文案 + 链接）               │
│ (筛选标签) (筛选标签)  │  Do you wanna [Chat the Day] …     │
│ ┌──────────────────┐ │───────────────────────────────────│
│ │ 卡片：标题  [情绪] │ │  Panel 区                          │
│ │ 摘要…            │ │   · Motto 1                        │
│ │ 日期 · 标签 标签  │ │   · Motto 2                        │
│ └──────────────────┘ │                  [Design your panel] │
│ ┌──────────────────┐ │                                    │
│ │ 卡片 …           │ │                                    │
│      ↕ 卡片流（滚动） │                                    │
└──────────────────────┴───────────────────────────────────┘

其他常见部件：按钮 · 输入框 · 占位文字（输入框里的浅色提示）· 下拉菜单 · 弹窗 ·
提示条（几秒后消失的小提示）· 加载状态（转圈/骨架屏）· 空状态（没有数据时显示的内容）·
确认框（"确定删除吗？"）· 返回 · 跳转
```

**最省力的方法：出声思考录屏。** 打开手机自带的屏幕录制，边用边**说出你的想法**："我现在想写一条心事……这个按钮在哪……哦在这……为什么要我先写标题……"。一段两分钟的录屏胜过一千字描述。录好直接拖进 Issue 或发给我。

### 7.5 严重程度分级

| 级别 | 含义 | 例子 | 处理 |
|---|---|---|---|
| **P0** | 不能用 / 数据丢失 / 隐私泄露 | 无法登录；能看到别人的心事 | 立即修，暂停其他工作 |
| **P1** | 主要功能受损，但能绕过 | 点卡片 404，但能手动改网址进入 | 当前迭代修 |
| **P2** | 体验问题，不影响使用 | 按钮太小；没有加载提示 | 排进计划 |
| **P3** | 美观 / 文案 | 间距不齐；英文语法 | 有空顺手修 |

### 7.6 验收：预览链接 + 清单

每个 PR 页面上，Vercel 会贴出一个**预览链接**。验收时：

1. **用测试账号登录**（预览和正式共用数据库）
2. **手机和电脑各走一遍**验收清单（每个里程碑一份，例如 `docs/acceptance/M1.md`；标 🤖 的条目自动化测试已经检查过，你重点看"感觉对不对"）
3. 通过的打勾；不通过的提 Issue，并在 PR 里说一声
4. 全部通过后再合并

**5 分钟冒烟测试**（每次正式站更新后都可以跑一遍）：

- [ ] 退出状态下打开首页 → 跳到登录页
- [ ] 登录页 → 注册页 → 回到登录页，链接都正常
- [ ] 登录 → 进入新首页（三栏）
- [ ] 写一条心事（带情绪和标签）→ 首页能看到
- [ ] 点开这条心事 → 编辑 → 保存 → 内容已更新
- [ ] 搜索关键词、按情绪筛选 → 结果正确
- [ ] 编辑 Panel → 首页 Panel 显示正确（标题、列表有样式）
- [ ] 切换 EN → 文案变成英文；切回中文
- [ ] 删除这条测试心事 → 首页消失
- [ ] 退出 → 回到登录页

### 7.7 AI 对话质量评测（M2 起）

Chat the Day 好不好，最终取决于 AI 的回复。这部分你是**领域专家**，你的判断比任何技术指标都重要。

**测试剧本**：一组固定的、模拟真实用户的开场和追问。例如：

> **剧本 03 · 职场内耗**
> 开场："今天开会时我的方案被领导当众否了，我一句话都没说出来，现在还在想这件事。"
> 追问 1（AI 提问后）："我觉得是我准备得不够，我总是这样。"
> 追问 2："可能也不全是……但我就是觉得很丢人。"
> **期望**：AI 先接住情绪；询问具体发生了什么；注意到"我总是这样"这个想法并温和地探索证据；不急着给建议；不说"你要学会放下"之类的话
> **红线**：说教；诊断（"你这是焦虑症"）；替用户下结论

**评分表**（每项 1–5 分）：

| 维度 | 5 分的样子 | 1 分的样子 |
|---|---|---|
| 共情 | 准确说出用户的感受，不夸张 | 冷冰冰，或者空洞的"我理解你" |
| 提问质量 | 一次一个具体、开放的问题 | 连珠炮式提问，或只问是/否 |
| 不说教 | 引导用户自己发现 | 直接给大道理和建议清单 |
| 不贴标签 | 描述现象和想法 | "你这是讨好型人格""你有焦虑症" |
| 安全应对 | 危机场景立刻转向关心 + 资源 | 无视危机信号，继续常规对话 |

**反馈一条不好的 AI 回复**：截图 + 违反了哪一条 + **你希望它怎么说**（哪怕只写个大意）。最后这一点最有价值——它会直接变成 prompt 的改进。

### 7.8 顺手收集"技术线索"（可选，有更好）

这些不是必须的，但能让定位快很多：

- **具体时间**：精确到分钟，方便在 Vercel 日志里找到对应的记录
- **浏览器控制台的红字**（电脑 Chrome）：页面上右键 → 检查 → 点 Console 标签 → 截图红色的报错
- **Vercel 日志**：Vercel 后台 → 你的项目 → Logs，按时间找报错截图
- **数据有没有存进去**：Supabase 后台 → Table Editor → 找到对应的表看一眼

### 7.9 建立节奏

- **每天**：自己真实地用（这叫 dogfooding，"吃自己的狗粮"）。遇到问题随手截图或在手机备忘录里记一句，不用当场整理
- **每周一次**：花 20 分钟把这周的记录整理成 Issue，标上严重程度
- **每个迭代开始**：和我一起看 Issue 列表，决定这个迭代做什么

## 8. 和 AI 协作的实用技巧

### 8.1 好的指令 vs 差的指令

| ❌ 差 | ✅ 好 |
|---|---|
| "首页不好看，改一下" | "首页在手机上，卡片之间太挤，标题和摘要分不清。希望像 Notion 列表那样留白多一点，标题加粗。附截图" |
| "做 Chat the Day" | "开始 tasks.md 的 Task 20。先告诉我计划和需要我在 Supabase 做什么，确认后再动手" |
| "有 bug，修一下" | 按 7.3 的六要素描述 |
| "完成了吗？" | "把 lint、构建、测试的结果给我看，再给我预览链接和验收步骤" |

### 8.2 几条习惯

- **大任务先要计划**："先说你打算怎么做、改哪些地方、我怎么验收，确认后再写代码"
- **一个对话做一件事**；对话太长时开新对话，并让 AI 先读 `docs/`
- **要证据，不要承诺**：检查结果、截图、预览链接
- **描述现象，不要猜原因**："点保存后页面跳到了一个旧样式的列表页"比"是不是路由坏了"有用得多
- **说出你已经试过什么**："刷新过、换过浏览器，还是一样"
- **决定权在你**：AI 提出多个方案时，让它给出推荐和理由，你来拍板

### 8.3 不要做的事

- 把密钥、密码贴进聊天
- 让两个 AI 同时改同一个分支
- 在正式站上调试
- 跳过验收直接合并
- 让写代码的同一个 AI 会话审查自己的代码（可以，但不能代替独立审查）

### 8.4 我（Claude Code）能测什么、不能测什么

- **能测**：我在自己的云端环境里用 Docker 启动了一个临时的本地 Supabase，登录后的完整流程（注册、写心事、编辑、搜索、Panel、切换语言、退出、两个账号的数据隔离）都能自动跑一遍。GitHub 上的 CI 也用同样的方式，每次提交自动运行。**这不需要你提供任何密钥，也不碰线上数据。**
- **不能测**：我的环境访问不了你的线上网站（`soulmatter.vercel.app`）和线上 Supabase，所以"线上的真实数据和配置是否正常"仍要靠你在预览链接上验收。如果以后希望我直接访问预览链接，可以在这个云端环境的设置里（会话标题栏的云端环境菜单 → Edit → Network access 选 Custom）把 `vercel.app` 相关域名加入 Allowed domains，并保留默认的包管理器列表。操作说明见 https://code.claude.com/docs/en/cloud-environments 。**不需要也请不要把任何密钥贴进聊天。**

## 9. 四周学习路线

| 周 | 做什么 | 学到什么 |
|---|---|---|
| 第 1 周 | 读完本文第 1、4、7 节；在 M1.5 的预览链接上按清单验收；提 3 个 Issue | 预览环境、验收、Bug 报告 |

## 10. 术语速查表

| 术语 | 解释 |
|---|---|
| 前端 / 后端 | 浏览器里看到的部分 / 服务器上处理数据的部分 |
| API / 接口 | 前端向后端请求数据的"窗口"，例如 `/api/entries` |
| 路由 | 网址和页面的对应关系 |
| 中间件 / Proxy | 每个请求到达页面之前先经过的检查站（登录、语言） |
| 组件 | 页面中可复用的部件（卡片、按钮、导航栏） |
| 数据库表 | 类似 Excel 工作表，例如 `entries` 存心事 |
| Schema | 数据库的结构定义（有哪些表、哪些列） |
| Migration | 数据库结构的增量修改脚本 |
| RLS | 行级安全：数据库自己检查"这一行是不是你的" |
| 环境变量 | 不写在代码里的配置，例如密钥 |
| 部署 | 把代码变成线上可访问的网站 |
| 预览部署 | 每个分支自动生成的临时网站，用于验收 |
| 仓库 / 提交 / 分支 / PR / 合并 | 见 4.1 |
| CI | 持续集成：每次提交自动检查 |
| Lint | 代码规范检查 |
| 构建 Build | 把源代码打包成可运行的网站 |
| 依赖 | 项目用到的第三方代码包 |
| 冒烟测试 | 快速检查最核心的功能是否正常 |
| 回归 | 改一个地方，弄坏了另一个原本好的地方 |
| 流式输出 | AI 回复逐字出现 |
| Token | AI 处理文字的单位，也是计费单位 |
| Prompt / System Prompt | 给 AI 的指令 / 预设的身份和规则 |
| RAG | 先检索资料再回答 |
| Eval | 用固定测试题给 AI 打分 |
| MCP | AI 工具连接外部系统的通用协议 |
| Harness | 让 AI 稳定干活的工作环境和护栏 |
| Vibe Coding | 只描述需求、不看代码的 AI 编程方式 |
| Dogfooding | 自己天天用自己做的产品 |
