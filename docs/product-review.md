## 0. 一句话结论

**方向是对的，排序需要调整。** 你的产品真正与众不同的地方是"用循证心理学**引导**用户自己想清楚"，以及"把想清楚的结论变成日常提醒"。但当前计划把"引导"的核心（system prompt、知识库）排到了最后（Phase 3），把"结论 → 行动"的连接排成了一个独立的 AI 推荐功能（M4）。这样做的结果是：M2/M3 上线的会是一个"普通的 AI 聊天框"，正好是你在 spec 里说要避免的"情感马杀鸡"。

另外，**M1 在线上存在几处影响使用的 bug**（详见第 3 节），建议先花一个小迭代修好、并把"自动检查"建起来，再进入 Chat the Day。

## 1. 我理解的你的目标

把 spec 里的描述提炼成一个循环，这是整个产品的"骨架"：

```
     ①记录                ②觉察                 ③行动                 ④复盘
  便捷地说出来  ──▶  AI 科学引导，自己得出  ──▶  结论变成 Panel 上的  ──▶  回头看：我变了吗？
 (Chat / 手动)        结论（Conclusion）          Motto，日常看到            (Look back)
       ▲                                                                       │
       └───────────────────────────────────────────────────────────────────────┘
```

每个功能都应该服务于这个循环中的某一环，并且**环与环之间要真正连起来**。一个循环只要有一环断了，用户就很难形成习惯。

另外两个隐含但重要的事实：
- **第一个用户就是你自己**。"自己和朋友用"意味着前几个月最重要的指标是：你自己是否愿意每周用 3 次以上。
- **这是一个心理健康相邻的产品**。即使不商业化，只要朋友在用，"安全"和"隐私"就不是可选项。

### 2.1 关于"科学引导"——建议把 prompt 设计提前到 M2

好的引导不一定需要知识库。DeepSeek 本身已经掌握 CBT（认知行为疗法）、ACT、DBT 的基础知识。真正决定对话质量的是 **system prompt 的结构**，例如参考 CBT 的"思维记录"（Thought Record）框架，让 AI 按这个节奏陪用户走：

1. **情境**：发生了什么？（具体的时间、地点、人）
2. **情绪**：当时什么感受？强度 0–10？
3. **自动想法**：那一刻脑子里冒出的念头是什么？
4. **证据检验**：支持/不支持这个想法的事实各有哪些？（苏格拉底式提问，而不是直接给答案）
5. **平衡的想法**：换个角度怎么看？——**由用户自己说出来**，这就是你设计的 Conclusion

你要求"Conclusion 必须由用户手写、AI 不代写"，这恰恰符合 CBT 的核心原则：改变来自用户自己的重新评估，而不是被告知。这是整个 spec 里最好的一个产品决策，应该围绕它来设计 prompt。

**建议**：M2 就上线"引导 prompt v1"，同时准备一套**测试剧本**（10–15 个典型心事场景，包括危机场景），每次改 prompt 都跑一遍、打分。这套剧本由你来写和评分最合适——你比任何工程师都更清楚"好的引导"是什么感觉。

### 2.2 关于"实时总结"——建议改为"结束时总结"

spec 设计的是对话过程中左侧实时显示 Topic/Content/Mood/Tag。建议改为**用户点"结束今天的对话"时，一次性生成总结**：

- **体验更好**：倾诉时旁边有个面板在不断"给你贴标签"，会让人分心，也有被分析的感觉
- **手机上放得下**：手机没有"左侧"
- **更便宜、更简单**：每轮都总结 = 每轮多一次 AI 调用
- **流程更自然**：结束 → 看到 AI 帮你整理的卡片（可修改）→ 写下自己的 Conclusion → 保存 → 可选"加到我的 Panel"

实时侧栏可以作为以后的增强功能保留在 Backlog 里。

### 2.3 关于数据结构——建议不建 `conversation_summaries` 表

总结的内容（Topic → 标题、Content → 内容、Mood、Tag）和 `entries` 表的字段一一对应。建议直接在 `entries` 表上加两个字段：
- `conversation_id`：这条心事来自哪次对话（手动记录则为空）
- `conclusion`：我的结论（**手动记录也可以填**——这样两种记录方式都能进入"觉察"环节）

少一张表，少一份同步逻辑，首页卡片流也天然统一。

### 2.4 安全（危机应对）——必须和 Chat 同时上线

任何允许人倾诉心事的 AI 产品，都会遇到用户表达自伤/自杀念头的时刻。即使只有朋友在用，也需要：

1. **Prompt 层**：明确规定 AI 在识别到危机信号时，停止常规引导，以温和、直接的方式表达关心，并给出求助资源
2. **界面层**：显示一张固定的"求助资源"卡片（例如 12356 全国心理援助热线等——**上线前由你核实号码和服务时间**）
3. **知情同意**：第一次使用 Chat the Day 时，用一屏说明：AI 不是心理咨询师；数据存在哪里、谁能看到；遇到紧急情况该找谁
4. **测试剧本**里必须包含 2–3 个危机场景，每次改 prompt 都要验证

### 2.5 隐私——承诺与实现需要对齐

现在有三处说法不一致：

| 来源 | 说法 |
|---|---|
| README | "AI 分析的原始心事内容不持久化存储" |
| spec | "原始心事正文用于检索但脱敏处理" |
| tasks（M2 计划） | `messages` 表存全部对话原文；`ai_logs` 表**再存一遍**完整 prompt 和回复 |

还有一个必须诚实面对的事实：**你作为 Supabase 项目的所有者，可以在后台看到所有用户的数据**（RLS 只限制通过 App 的访问，不限制项目管理员）。对于你自己的数据这没关系；但朋友用之前，他们应该知道这一点，以及数据会发送给 DeepSeek 处理。

**建议**：
- 在产品里写一页简短、诚实的隐私说明（存了什么、谁能看到、发给了谁、怎么删除）
- `ai_logs` 存完整内容便于调试，但设定保留期（如 30 天自动清理）
- "导出我的数据"和"删除我的全部数据"提前到邀请朋友之前（工作量不大）
- 更新 README 和 spec 中不准确的说法

### 2.6 其他小建议

- **语音输入**：先不开发。手机输入法（iOS/安卓）都自带语音转文字按钮，直接可用
- **手动记录的标题改为可选**：留空时自动取内容第一句，降低记录门槛
- **首页文案**：`Look back your changes recently` 语法上应为 `Look back on your recent changes`
- **成功标准**：建议在 spec 里加一节"怎样算这个产品有用"，例如：
  - 我自己连续 4 周、每周记录 ≥ 3 次
  - 回看 Conclusion 时，至少一半让我觉得"当时想通了一些东西"
  - 每次对话结束有 👍/👎 反馈，👍 比例作为 prompt 质量的参考
- **先自己用 4 周，再邀请朋友**：产品早期最宝贵的反馈来自每天使用它的你

## 3. M1 现状核查（2026-10-06）

我在本地构建并运行了当前 `main` 分支，逐个路由测试，并通读了全部代码。`tasks.md` 中 Task 10–14 标记为 `completed`，但 Task 15（M1 联调验收）仍是 `pending`。实际检查发现：

### 3.1 影响使用的问题

| # | 严重度 | 问题 | 你在线上会看到的现象 |
|---|---|---|---|
| B1 | 🔴 高 | 语言中间件（next-intl）创建了但**从未被调用**；并且不带 `/zh` 前缀的地址都被当成首页处理 | 登录页点"注册"会被**弹回登录页**；已登录时，首页点任意心事卡片 → **404**；新建/编辑心事保存后 → 404；删除心事后 → 404；详情页"返回列表" → 404 |
| B2 | 🔴 高 | 首页"退出"按钮提交到一个不存在的地址 `/auth/signout` | 首页点"退出"无法退出（报错页） |
| B3 | 🔴 高 | 全局导航栏（含"写心事"按钮）没有被任何页面使用 | 首页**没有"写心事"入口**；详情/编辑/新建页没有导航栏，也没有页面边距（内容贴边） |
| B4 | 🟡 中 | Panel 用了 `prose` 样式类，但没有安装对应的 Tailwind Typography 插件 | Panel 里的 Markdown 标题和正文一样大，列表没有圆点——看起来像"没渲染" |
| B5 | 🟡 中 | 页面根部有两层 `<html><body>` 嵌套 | 浏览器控制台报错，可能引起样式异常 |
| B6 | 🟡 中 | 手机开启深色模式时，背景/文字颜色只改了一部分 | 部分标题和 Panel 文字在白色卡片上变成近白色，**几乎看不见** |
| B7 | 🟡 中 | 多语言只接入了框架：首页、登录/注册、卡片流、筛选器、情绪标签等仍是写死的中文 | 切换到 EN 后大部分文字仍是中文（AC-13 实际不通过） |
| B8 | 🟡 中 | 根地址 `/` 仍重定向到旧的 `/zh/entries` 列表页（Task 13 要求删除该页但未删除） | 已登录时直接打开 soulmatter.vercel.app，或保存 Panel 后，进入的是样式不同的旧列表页，而不是新首页 |
| B9 | 🟢 低 | 首页只加载最近 20 条，搜索只在这 20 条中进行 | 搜不到较早的心事 |
| B10 | 🟢 低 | 移动端堆叠顺序与 Task 13 约定不一致（约定 Panel 在上，实际卡片流在上） | — |
| B11 | 🔴 高 | （修复时发现）注册成功后跳转的网址里带中文提示文字，服务端报错 | 点"注册"后页面停住没反应，但账号其实已经建好了 |

> 验证方式：B1、B2 在本地用"模拟已登录"的方式实际请求确认（`/entries/xxx`、`/entries/new`、`/register`、`/auth/signout` 均返回 404）；其余来自代码通读和构建产物检查。我目前无法访问你的线上网站和 Supabase，所以线上表现以你实际操作为准——你可以照着"现象"一列试一下。

### 3.2 质量检查

- `npm run build`：✅ 通过
- `npm run lint`：❌ **6 个错误、2 个警告**（Task 15 的验收要求是 0 错误）
- `middleware.ts`：Next.js 16 已将此约定更名为 `proxy.ts`（目前仍可运行，但已弃用）

### 3.3 为什么会这样？（这比 bug 本身更值得关注）

这些问题不是因为某个 AI 不够聪明，而是**流程上缺了三道关**：

1. **"完成"由写代码的一方自己宣布**。Task 标记为 completed，但验收要求里的截图证据并不存在，`lint 0 错误` 也没有达到
2. **没有自动检查（CI）**。如果每次提交都自动跑一遍 lint 和构建，B5、lint 错误会被立刻拦下
3. **M1 跳过了独立审查**。Phase 1 时你做过一次独立审查（`review.md`），第一轮就发现了一个高危的数据权限漏洞——这个好习惯在 M1 没有延续

这三道关正是《工程化入门指南》（`docs/engineering-guide.md`）第 4、6 节要讲的内容。新的任务计划里，每个里程碑都以"自动检查通过 + 你在预览链接上按清单验收"结束。
